근무표 활동 구간 재구성

신규 활동 시간에 맞춰 기존 근무활동을 분할하고 앞뒤 잔여 구간을 보존하는 시간 구간 재구성 로직 개발

상황

상담사 근무표는 기본 근무 위에 점심, 회의 같은 활동이 겹쳐 들어옵니다. 관리자가 30분 단위 시간표에 활동을 끌어다 놓으면, 하나의 입력이 여러 기존 활동에 동시에 걸칩니다.

한 일

  • 겹친 활동마다 신규 활동 앞뒤로 남는 시간을 원래 활동으로 보존하도록 서버에서 구간을 다시 구성
  • 근무활동 상세가 시작 시각 기준으로 한 건만 존재하는 구조에 맞춰, 시작 시각이 같으면 기존 행을 삭제하고 새 행을 삽입
  • 빈 칸이나 기본 근무 밖에 넣은 연장근무 같은 활동은 신규로 등록하고, 같은 활동을 같은 자리에 다시 넣으면 막음
  • 철야조 근무표가 시각 기준 정렬로 순서가 뒤집히던 문제를 날짜를 포함한 일시 기준 정렬로 수정
  • 여러 행의 삭제/삽입을 한 처리 단위로 묶어 중간 오류 시 전체 롤백

    휴가를 반영한 스케줄 생성

    반차, 반반차, 종일휴가를 근무시간 구간에 반영하는 스케줄 생성 로직 개발

    상황

    철야조는 소정근로시간이 주간과 달라 반차 시간을 고정값으로 쓸 수 없었습니다. 하루에 휴가가 여러 건 들어오고, 오전/오후 휴가 사이에 점심이 끼어 시간이 이어지지 않는 경우도 있었습니다.

    한 일

    • 철야조는 반차 시간을 소정근로시간 절반으로 계산하고, 오전은 30분 단위 내림, 오후는 올림으로 맞춤
    • 종일 여부를 시간 연속이 아니라 일자별 휴가 시간 합계로 판정
    • 종일휴가 처리를 근무 상세 전체 삭제에서, 근무시간만큼 휴가 구간을 등록하는 방식으로 변경

    근무 이행률 현황

    30분 단위로 스케줄된 근무활동과 실제 상담 실적을 맞대어 상담사별 근무 이행률을 보여주는 통계 화면 개발

    상황

    관리자는 상담사가 스케줄대로 일했는지를 시간대별로 확인해야 합니다. 스케줄은 근무표에, 실제 상담 실적은 CTI에서 15분 단위로 쌓여 두 데이터의 기준이 서로 달랐습니다.

    한 일

    • 30분 칸마다 그 시간의 근무활동과 상담 실적을 맞대어 이행률을 산출. 스케줄상 상담 시간 대비 수신, 발신, 대기 같은 상담 실적 시간으로 계산
    • 15분 단위 실적을 30분 칸으로 묶고, 자정을 넘는 야간조 실적은 근무일 기준으로 귀속
    • 일자와 월 이행률은 칸 이행률의 단순 평균이 아니라 실적 시간 합계를 상담 시간 합계로 나눈 가중평균으로 산출하고, 시간대별 화면에서 일자별 조직/개인 화면과 월 평균까지 같은 기준으로 확장
    • 300초 걸리던 조회 쿼리에서 같은 계산이 반복 실행되는 구조를 찾아 20초 이내로 단축하고, 환경마다 이행률 일부가 비던 원인을 중복행과 순서에 의존한 변환 로직으로 규명해 수정

    운영 결함 원인 추적

    운영 중 발생한 결함을 데이터 흐름을 따라 추적해 원인을 확인하고 수정

    접근 방식

    화면에서 보이는 증상만 막지 않고, 화면이 서버로 보내는 데이터와 서버가 짝짓는 기준, DB 조건까지 따라가 실제 원인을 확인한 뒤 고쳤습니다.

    증상, 원인, 수정
    증상원인수정
    여러 날짜에 같은 변경을 일괄 적용하면 일부 날짜만 저장됨 변경 전후 데이터를 짝짓는 키에 근무일자가 빠져 다른 날짜끼리 묶임 근무일자를 포함한 키로 변경
    30분 칸 하나에 10분 단위 활동이 여러 건이면 일부가 화면에서 사라짐 조회 결과를 시간표로 바꾸는 Java 로직이 같은 칸 데이터를 덮어씀 같은 칸의 활동을 모두 표시하도록 변환 로직 수정
    활동 재등록 시 PK 중복 오류 삭제 조건이 테이블 PK와 맞지 않아 기존 행이 남음 삭제 조건을 PK 기준으로 맞추고 재삽입 전 선삭제

    CTI 데이터 수신 API 구조 변경

    건별 DB 저장 완료 후 응답하던 구조를 Spring @Async 기반으로 변경하여 요청 접수 응답과 저장 작업 분리

    상황

    외부 CTI 업체가 2초/15분 주기로 상담사 통화/통계 데이터를 JSON으로 보냅니다. 대량 데이터를 모두 저장한 뒤 응답하다 보니, 앞 요청이 끝나기 전에 다음 요청이 계속 들어와 응답 지연과 메모리 부족 오류가 발생했습니다.

    한 일

    • @Async로 요청 접수 응답과 DB 저장을 분리
    • 운영 확인용으로 수신 원문을 설정값에 따라 저장하고 조회하는 로그 기능 개발

    지금 다시 한다면

    비동기 작업이 쌓이지 않도록 스레드 풀 크기와 대기열 상한을 두고, 저장 실패 건을 기록해 다시 처리할 수 있게 하겠습니다.

    변경 전
    1. CTI 업체 요청2초마다 데이터 전송
    2. 건별 MERGE 반복전부 끝날 때까지 대기
    3. 응답다음 요청이 앞 작업 위에 쌓임
    변경 후
    1. CTI 업체 요청2초마다 데이터 전송
    2. 접수 응답저장을 기다리지 않음
    3. @Async 저장별도 스레드에서 MERGE

    응답은 접수 결과이고 저장 완료를 뜻하지 않습니다. 그래서 수신 원문 로그로 운영 중 확인할 수 있게 했습니다.

    AS-IS 분석과 통계 쿼리 이관

    AS-IS(MiPlatform) 화면 및 쿼리 분석을 통한 Nexacro N24 기반 TO-BE 시스템 이관

    한 일

    • 시간대, 기간, 조직, 스킬별 콜통계와 실시간 상담원 모니터링 화면의 Oracle 쿼리 작성
    • AS-IS 쿼리의 산식을 분석해 TO-BE 테이블 구조로 옮기고, 같은 조건의 결과값을 대조해 차이를 수정
    • 근무가 자정을 넘는 야간근무의 일자 기준 집계 처리
    이관 절차
    1. AS-IS 화면과 쿼리 분석지표별 산식과 조건 파악
    2. TO-BE 구조로 재작성새 테이블 기준 Oracle 쿼리
    3. 결과값 대조같은 기간/조건으로 AS-IS와 비교
    4. 차이 원인 수정산식, 분모, 일자 기준 맞춤
